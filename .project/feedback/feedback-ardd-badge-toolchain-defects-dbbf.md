# Feedback

All items here are defects in the upstream ArDD toolchain (`~/.ardd/source`),
not in this repo's own code. They are recorded here because this is where
they were found; carrying them upstream is the actual resolution.

## Bugs
- [ ] F001 Upstream ArDD `install.sh` records a stable `Source-Ref` on a beta-channel install. Root cause is in the `ALL_REFS_AT_HEAD` block (`install.sh`, ~L574-576): it unconditionally prefers a non-`-beta.` tag, then orders with a plain `sort -V`. Both halves are wrong for a commit carrying `v1.2.0` *and* `v1.2.1-beta.1` (this repo's exact state at `20d8960`): the preference is channel-blind, so a `Channel: beta` install cannot record a beta ref at all; and plain `sort -V` lacks the `versionsort.suffix=-beta.` config that the sibling `source-resolve.sh` (L156) applies for precisely this ordering, even though `install.sh`'s own comment claims to be "matching the ordering convention used elsewhere (next-version.sh, source-resolve.sh)". The guarded-against case — a stable cut still carrying the beta it was promoted from, e.g. `v1.2.0` + `v1.2.0-beta.3` — is real, but the heuristic over-generalizes to a *newer* prerelease. Suggested fix: pick the highest tag under `versionsort.suffix=-beta.` ordering, filtered to the channel being recorded. This is not cosmetic: `.github/workflows/ardd-badge.yml` reads `Source-Ref` verbatim into the badge `message`, so a beta install publicly advertises a stable version string.
- [ ] F002 Upstream ArDD `templates/badge-shieldcn.md`'s `PLACEHOLDER` caveat is stale. Its header and "Renderer caveat" comment both assert (verified upstream 2026-07-21) that shieldcn.dev's `dynamic/json` `logo=` param silently ignores a `data:image/svg+xml;base64,...` URI, and ship `PLACEHOLDER` in the shape-2/shape-3 snippets for that reason. Re-running the same A/B byte-comparison on 2026-07-24 against this repo's live badge URL shows the opposite: with the data-URI logo the SVG grows 3929 -> 4133 bytes, width 190 -> 212, and the added `<path d="M12 2 22.5 21H1.5ZM12 8.2 17.4 18H6.6Z">` is the ArDD mark from `.github/badges/ardd-icon.svg` itself. shieldcn.dev added data-URI support since that verification; the template should drop `PLACEHOLDER` and inline the real base64 icon.
- [ ] F003 Upstream ArDD `scripts/completion-flip-check.sh` fails silent once the merged branch is deleted — defeating it in exactly the scenario it exists for. It resolves a branch (the tasks file's `worktree_branch:`, else the plan's `branch:`) and gates on `git merge-base --is-ancestor "$branch" "$default" 2>/dev/null`. When the branch ref no longer exists, that `git` call errors, the error is swallowed by `2>/dev/null`, and the script `exit 0`s indistinguishably from "nothing orphaned". Deleting the branch on merge is GitHub's default post-merge action, so the common path is a permanent false negative. Observed here: `tasks-1a23-cc11.md` is `completed`, its plan records `branch: 1a23` and all three bound features, PR #112 merged the work, all three features were still `tasked` — and the script printed nothing, because branch `1a23` was gone. The orphan had to be found by hand. Suggested fix: distinguish "branch missing" from "branch not merged" and report the former loudly (or fall back to locating the squash/merge commit) rather than treating an unresolvable ref as all-clear.
- [ ] F004 Upstream ArDD's `/ardd-update` skill and `install.sh` disagree about when to offer the dynamic version badge, so the skill can offer something the script then refuses to produce. The skill (step 4, "Dynamic version-badge offer") gates on the README *not* containing `ardd-badge-version-start`; `install.sh`'s `BADGE_FAMILY` guard (~L729-737) checks the three marker families in priority order and classifies a README carrying only `ardd-badge-start` as `static`. A README whose badge block sits under the static markers therefore satisfies the skill's "go ahead and offer" test while `install.sh` — even with `ARDD_VERSION_BADGE=1` — prints "README is already badged via static markers" and never emits the snippet. Hit live on this repo this run: the offer was made, accepted, and could not be fulfilled. The two guards should test the same condition.

## UX
- [ ] F005 Upstream ArDD's shieldcn badge templates should document that shieldcn.dev ignores `mode=`. `templates/badge-shieldcn.md` is silent on light/dark rendering, which leaves adopters to invent their own theme handling — this repo had wrapped both its shieldcn badges in a `<picture>` + `<source media="(prefers-color-scheme: dark)">` block passing `mode=dark`/`mode=light`. That wrapper was locally authored, *not* suggested by any ArDD template (no template mentions `picture` or `prefers-color-scheme`), so this is a documentation gap rather than a template defect. Verified 2026-07-24: `mode=dark`, `mode=light`, and no `mode` at all return three byte-identical SVGs, as does the sponsor badge and the npm group badge. A one-line note in the renderer caveat would prevent the dead markup.
- [ ] F006 Upstream ArDD's shipped `templates/ardd-badge-workflow.yml` computes a per-channel `color` that is inert under the renderer `install.sh` offers by default. The workflow derives `yellow` for beta / `blue` for stable into the endpoint JSON, but shieldcn's `dynamic/json` reads only the `query`-selected field — verified 2026-07-24 that it ignores both the JSON's own `color` and a `colorQuery=$.color` selector — so the colour only reaches a badge if it is duplicated by hand as a static `color=` URL param (as this repo now does). Since `badge-shieldcn.md` is documented as the default offer, the default pairing ships a computed value that silently does nothing. Either note the manual mirroring in the template, or default the badge to a shields.io `/endpoint` render, which does consume the JSON's `color`, `labelColor`, and `logoSvg`.
